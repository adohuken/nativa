1. RESUMEN EJECUTIVO Y FICHA TÉCNICA
================================================================================
Nativa es una plataforma web orientada a la adquisición natural de segundas lenguas
(SLA) basada en el modelo de Input Comprensible (i + 1) de Stephen Krashen,
enfocada en evitar la traducción mental mediante inmersión contextual, fonética IPA,
evaluaciones formativas de baja ansiedad y preparación para entornos BPO/Universitarios.

* Arquitectura de Producción Activa:
  - Framework: Next.js 16.4.6 (App Router, Turbopack / Webpack).
  - UI & Estilos: React 19, Tailwind CSS 4, Framer Motion, Lucide Icons.
  - Base de Datos y Autenticación: Supabase (PostgreSQL managed, Auth, Row Level Security).
  - Síntesis y Reconocimiento de Voz: Web Speech API nativa (TTS & STT en cliente).
  - Despliegue e Infraestructura: Contenedor Docker multi-stage sobre servidor Dokploy
    (IP pública: 155.133.197.176 / Dominio: nativa.155.133.197.176.sslip.io).
  - Integraciones de IA: Soporte multi-proveedor para Google Gemini, Groq, OpenAI,
    Cerebras, Mistral, DeepSeek, OpenRouter, Cohere y Cloudflare AI.

* Diagnóstico Global:
  - Nivel Funcional: MUY ALTO (Plataforma rica en interactividad, audio multi-velocidad,
    shadowing con reconocimiento de voz, rúbricas pedagógicas automatizadas y gamificación).
  - Postura de Seguridad: VULNERABLE. Existen fallas severas en las políticas de seguridad
    de base de datos (RLS), validación de sesiones administrativas por cookies manipulables,
    almacenamiento de contraseñas en LocalStorage y endpoints de inteligencia artificial
    desprovistos de autenticación y límites de consumo.

4. AUDITORÍA DE SEGURIDAD Y MATRIZ DE VULNERABILIDADES
================================================================================

A continuación se detallan las vulnerabilidades identificadas durante la revisión
estática y dinámica del código fuente, ordenadas por criticidad:

--------------------------------------------------------------------------------
4.1. VULN-01 [CRÍTICA]: POLÍTICAS RLS PERMISIVAS EN SUPABASE (BYPASS DE PRIVILEGIOS)
--------------------------------------------------------------------------------
* Ubicación: web/supabase_schema.sql (Líneas 180 a 210 y 245 a 257)
* Descripción Técnica:
  Las políticas de Row Level Security (RLS) contienen cláusulas 'OR id IS NOT NULL'
  u 'OR user_id IS NOT NULL' otorgadas a los roles 'anon' y 'authenticated':
  
  Ejemplo en 'profiles':
  CREATE POLICY "Los usuarios pueden actualizar su propio perfil" 
    ON public.profiles FOR UPDATE 
    TO authenticated, anon
    USING (auth.uid() = id OR id IS NOT NULL)
    WITH CHECK (auth.uid() = id OR id IS NOT NULL);

* Impacto:
  Dado que 'id' es la clave primaria UUID de la tabla y NUNCA es nulo, la condición
  'id IS NOT NULL' siempre evalúa a TRUE. Esto significa que cualquier usuario anónimo
  o cualquier alumno registrado puede enviar un request UPDATE directo a Supabase
  usando la anon key pública y modificar CUALQUIER registro de la base de datos,
  pudiendo ejecutar:
  UPDATE profiles SET is_admin = true, is_premium = true WHERE email = 'cualquier_correo@...';
  Esto otorga privilegios totales de superusuario a cualquier atacante.

* Severidad: CRÍTICA (CVSS 9.8)

--------------------------------------------------------------------------------
4.2. VULN-02 [ALTA]: ALMACENAMIENTO DE CONTRASEÑA EN TEXTO PLANO EN LOCALSTORAGE
--------------------------------------------------------------------------------
* Ubicación: web/src/lib/storage.ts (Líneas 541-557)
* Descripción Técnica:
  La función 'updatePassword' y 'verifyCurrentPassword' almacena la contraseña
  del usuario en texto claro en el almacenamiento local del navegador:
  localStorage.setItem('fluentia_user_credentials', newPassword);

* Impacto:
  Cualquier ataque de Cross-Site Scripting (XSS), script de terceros o extensión
  maliciosa instalada en el navegador de los alumnos o administradores puede
  leer directamente la clave en texto sin cifrar mediante 'localStorage.getItem(...)'.

* Severidad: ALTA (CVSS 7.5)

--------------------------------------------------------------------------------
4.3. VULN-03 [ALTA]: FALSIFICACIÓN DE COOKIE EN MIDDLEWARE ADMINISTRATIVO
--------------------------------------------------------------------------------
* Ubicación: web/src/middleware.ts (Líneas 13-22)
* Descripción Técnica:
  El middleware que custodia las rutas '/admin' y '/admin/company/*' valida el
  acceso comprobando únicamente si existe una cookie de texto:
  const adminSessionCookie = request.cookies.get('nativa_admin_session')?.value;
  if (!adminSessionCookie || adminSessionCookie !== 'true') { ... }

* Impacto:
  Cualquier persona puede abrir la consola de desarrollador del navegador (F12) y escribir:
  document.cookie = "nativa_admin_session=true; path=/;";
  Con esto, el middleware permite el acceso hacia la ruta '/admin'. Si bien la página
  realiza una segunda validación con Supabase, si Supabase no está configurado o falla
  la conexión de red, la página /admin tiene como fallback:
  if (!client || !isSupabaseConfigured) { setIsAdminAuthorized(true); }
  otorgando acceso completo a la interfaz administrativa.

* Severidad: ALTA (CVSS 8.2)

--------------------------------------------------------------------------------
4.4. VULN-04 [ALTA]: ENDPOINTS DE IA EXPUESTOS SIN AUTENTICACIÓN NI RATE LIMITING
--------------------------------------------------------------------------------
* Ubicación:
  - web/src/app/api/ai/proxy/route.ts
  - web/src/app/api/ai/evaluate-project/route.ts
  - web/src/app/api/ai/test-key/route.ts
* Descripción Técnica:
  Los métodos POST de estas rutas no validan tokens de autorización (Bearer Token /
  Supabase JWT) ni identifican la sesión del usuario que realiza la petición. Tampoco
  poseen limitadores de peticiones por minuto (Rate Limiting).
* Impacto:
  Cualquier usuario o bot externo puede enviar peticiones masivas a estos endpoints
  utilizando las API keys del servidor (Gemini, Groq, OpenAI, etc.) de forma gratuita,
  agotando las cuotas de tokens, bloqueando el servicio para alumnos legítimos o
  generando sobrecostos económicos en las cuentas de IA asociadas.

* Severidad: ALTA (CVSS 7.6)

--------------------------------------------------------------------------------
4.5. VULN-05 [ALTA]: TOKEN PERSONAL DE GITHUB ACTIVO EN CONFIGURACIÓN GIT Y SCRIPTS
--------------------------------------------------------------------------------
* Ubicación:
  - .git/config (Remote URL de git)
  - subir_con_token.bat (Rastreado en el repositorio)

5.1. SCRIPT SQL CORREGIDO PARA SUPABASE (BLINDAJE DE RLS)
--------------------------------------------------------------------------------
Ejecuta el siguiente bloque en el SQL Editor de tu Dashboard de Supabase para
anular de inmediato las políticas inseguras y restringir cada operación únicamente
al dueño legítimo autenticado:

```sql
-- 1. Eliminar políticas inseguras
DROP POLICY IF EXISTS "Los usuarios pueden ver su propio perfil" ON public.profiles;
DROP POLICY IF EXISTS "Los usuarios pueden insertar su propio perfil" ON public.profiles;
DROP POLICY IF EXISTS "Los usuarios pueden actualizar su propio perfil" ON public.profiles;
DROP POLICY IF EXISTS "Los usuarios pueden ver su propio progreso" ON public.user_progress;
DROP POLICY IF EXISTS "Los usuarios pueden modificar su propio progreso" ON public.user_progress;
DROP POLICY IF EXISTS "Los usuarios pueden ver su propio vocabulario" ON public.user_vocabulary;
DROP POLICY IF EXISTS "Los usuarios pueden agregar palabras a su vocabulario" ON public.user_vocabulary;
DROP POLICY IF EXISTS "Los usuarios pueden actualizar su propio vocabulario" ON public.user_vocabulary;

-- 2. Políticas estrictas para PROFILES
CREATE POLICY "Lectura estricta de perfil propio o admin"
  ON public.profiles FOR SELECT
  TO authenticated
  USING (auth.uid() = id);

CREATE POLICY "Inserción estricta de perfil propio"
  ON public.profiles FOR INSERT
  TO authenticated
  WITH CHECK (auth.uid() = id);

-- Impedir que un alumno pueda cambiarse a is_admin = true
CREATE POLICY "Actualización estricta de perfil propio (sin auto-promoción a admin)"
  ON public.profiles FOR UPDATE
  TO authenticated
  USING (auth.uid() = id)
  WITH CHECK (
    auth.uid() = id 
    AND (
      is_admin = (SELECT p.is_admin FROM public.profiles p WHERE p.id = auth.uid())
      OR (SELECT email FROM auth.users WHERE id = auth.uid()) = 'adohuken2005@gmail.com'
    )
  );

-- 3. Políticas estrictas para USER_PROGRESS
CREATE POLICY "Lectura estricta de progreso propio"
  ON public.user_progress FOR SELECT
  TO authenticated
  USING (auth.uid() = user_id);

CREATE POLICY "Modificación estricta de progreso propio"
  ON public.user_progress FOR ALL
  TO authenticated
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

-- 4. Políticas estrictas para USER_VOCABULARY
CREATE POLICY "Lectura estricta de vocabulario propio"
  ON public.user_vocabulary FOR SELECT
  TO authenticated
  USING (auth.uid() = user_id);

CREATE POLICY "Inserción estricta de vocabulario propio"
  ON public.user_vocabulary FOR INSERT
  TO authenticated
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "Actualización estricta de vocabulario propio"
  ON public.user_vocabulary FOR UPDATE
  TO authenticated
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);
```
